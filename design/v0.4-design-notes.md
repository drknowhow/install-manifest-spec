# Install Manifest v0.4 — Design Notes

**Status:** v0.4 additive release, drafted 2026-05-16.
**Predecessor:** `design/v0.3.1-design-notes.md` (frozen).
**Schema:** `schema/install-manifest-v0.4.json`.

---

## Why v0.4 exists

v0.4 closes the two largest holes left open by v0.3.1, both surfaced by
Muninn's consumer-test rounds and both filed as repo issues with
fully-designed proposals attached. v0.3.1 was the additive-fixes pass
(small surface, six tiny gaps); v0.4 is the targeted gap-closer (two
structural patterns that v0.3 had no shape for at all).

Both new fields are strictly additive: every v0.3.1 manifest validates
against the v0.4 schema unmodified after a `manifest_version` bump. The
test suite proves this via the same Muninn-trio regression bed used for
the v0.3 → v0.3.1 transition.

Sources:

- [issue #4](https://github.com/drknowhow/install-manifest-spec/issues/4) —
  `data_boundary.transmits[]` cannot model variable-target outbound.
  Surfaced by `muninn-bsky-card`: a link-card poster that fetches
  whatever URL is shared. `to: "<host>"` doesn't fit; patterns are
  unverifiable; the v0.3 workaround was prose-in-rationale, which routes
  around the whole point of machine-readable blast radius.
- [issue #5](https://github.com/drknowhow/install-manifest-spec/issues/5) —
  `runtime.install` has no shape for tools pre-baked into the agent's
  runtime image. `muninn-bsky-card` took the half-fiction path with
  `method: "git"` + a `subpath` pointing at a directory not yet
  committed. Better to acknowledge the case structurally.

Both proposals went through one round of design review and shipped
exactly as designed. Nothing in v0.4 is speculative.

## What's new

### 1. `runtime.install.method: "preinstalled"` (issue #5)

A fifth variant in the `runtime.install.oneOf`. When `method ==
"preinstalled"`, the installer skips all acquisition steps; before
running `smoke`, it probes the locator to confirm the tool actually
exists in the runtime image. Without the locator probe, a missing
artifact silently passes install — exactly the failure mode the
manifest contract is supposed to prevent.

```json
"runtime": {
  "kind": "python-module",
  "install": {
    "method": "preinstalled",
    "locator": {
      "kind": "python-module",
      "module": "muninn_bsky_card"
    }
  },
  "entrypoint": { "command": ["python", "-m", "muninn_bsky_card"] }
}
```

**Locator kinds (initial set):**

| `kind` | required sibling | probe |
|---|---|---|
| `python-module` | `module` (string) | `importlib.import_module(module)` |
| `binary-on-path` | `binary` (string) | `shutil.which(binary)` returns a path |
| `mcp-server-id` | `server_id` (string) | host agent's MCP registry lists the server |

`locator` is required. Each kind variant is closed
(`additionalProperties: false`) so future fields land deliberately, not
as drift. The set is intentionally short: cover the runtimes Muninn-class
and Yep-class agents actually use today; add others when a real consumer
hits a real gap.

**Validator/runner expectations:**

- The schema enforces shape only.
- The CLI / installer is expected to (a) skip acquisition, (b) run the
  locator probe before `smoke`, and (c) surface a clear "tool not
  present in runtime" error if the probe fails. This is runtime behavior
  documented here for implementers; the schema itself can't enforce a
  probe.

**Why not just allow `method: "preinstalled"` with no locator?** Because
"the tool is already there" claims the agent's runtime image is
truth-checked before install completes. Without a probe, the claim is
unfalsifiable. The smoke step alone is not enough — `smoke` runs the
tool's own entrypoint, which can fail for reasons unrelated to presence
(network, args, env). The locator probe is the install-time honesty
check.

### 2. `data_boundary.transmits[].to_kind` and `to_constraint` (issue #4)

A transmits[] entry now declares its recipient in one of two shapes:

```json
// Shape A — fixed hostname (unchanged from v0.3)
{ "to": "api.openai.com", "fields": [...], "purpose": "...", "third_party_retention": "..." }

// Shape B — agent-supplied (new in v0.4)
{ "to_kind": "agent-supplied",
  "to_constraint": "https-only no-private-ranges",
  "fields": [...],
  "purpose": "...",
  "third_party_retention": "..." }
```

The schema enforces exactly-one-of `to` / `to_kind` via a `oneOf` at the
transmits-item level. Authors cannot set both, and cannot set neither.

**Why no patterns (`*.example.com`)?** Patterns invite manifest authors
to lie about blast radius. A claim of `"*.example.com"` is unverifiable
at install time — a validator cannot disprove it. `agent-supplied` is
honest by construction: the manifest says "the destination is whatever
the agent passes," and consent runners can use that as a louder warning
signal. Hostname-restricted tools keep using the existing `to: "<host>"`
shape (verifiable at runtime by intercepting outbound).

**`to_constraint` is prose, not policy.** A free-form ≤280-char string
describing what runtime checks the tool claims to apply
(`"https-only no-private-ranges"`, `"public DNS only, no RFC1918"`,
`"GitHub repository URLs only"`). The validator can't enforce it; the
field documents the tool author's safety claim for human reviewers and
for future v0.5 runtime enforcement.

**`third_party_retention` semantics for agent-supplied targets.** The
enum stays the same. Authors should declare the worst plausible case
across runtime recipients — typically `"unknown"`, sometimes `"session-only"`
if the tool never persists the URL it touched. Filing the field as
`"unknown"` is honest and visible; filing it as anything narrower is a
claim the consent runner can audit later if logs are available.

## Compatibility

v0.4 is **strictly additive** on top of v0.3.1 (and therefore v0.3).
Concretely:

- Every v0.3.1 manifest validates against the v0.4 schema unmodified.
  The test bed walks: minimal v0.3.1 + minimal v0.3 + `gmail.v0.3.json`
  + all three Muninn community manifests, each re-declared as v0.4.
- No v0.3.1 field changes meaning under v0.4. No narrowing on existing
  shapes. (The new `transmits[]` oneOf does add a structural rule, but
  v0.3.1 already required `to`; bare `to` is still the required shape
  in the absence of `to_kind`.)
- Agents that only support v0.3.1 should treat v0.4 manifests as
  readable only when the new fields are absent. Forward-ignore on
  security-relevant fields like `to_kind` would let an agent quietly
  treat an agent-supplied outbound as fixed-host (it has no `to`!), so
  the safer behavior is "reject v0.4 manifests if any new field is
  present and your runtime can't honor the contract."

The v0.3.1 narrowing (`data_boundary` required when `scopes[]` touches a
private-data resource prefix) carries forward unchanged. So does the
v0.3.1 `kill_switch.kind: "none"` honesty check (env-empty + persists-empty
when stateless).

## Worked example: muninn-bsky-card at v0.4

Combining both new fields, a corrected manifest for the case that
triggered both issues:

```json
{
  "manifest_version": "0.4",
  "tool": {
    "namespace": "muninn",
    "id": "bsky-card",
    "version": "0.1.0",
    "name": "Muninn — Bluesky Link Card",
    "summary": "Post a Bluesky note with an Open Graph card for an agent-supplied URL.",
    "homepage": "https://github.com/oaustegard/muninns-inbox"
  },
  "runtime": {
    "kind": "python-module",
    "install": {
      "method": "preinstalled",
      "locator": { "kind": "python-module", "module": "muninn_bsky_card" }
    },
    "entrypoint": { "command": ["python", "-m", "muninn_bsky_card"] }
  },
  "scopes": [
    { "resource": "net.outbound", "actions": ["read"], "rationale": "Fetch agent-supplied URL to extract Open Graph metadata." },
    { "resource": "bluesky.posts", "actions": ["write"], "rationale": "Publish the resulting link card." }
  ],
  "data_boundary": {
    "transmits": [
      {
        "to_kind": "agent-supplied",
        "to_constraint": "https-only no-private-ranges",
        "fields": ["/url"],
        "purpose": "Fetch URL for Open Graph metadata extraction.",
        "third_party_retention": "unknown"
      },
      {
        "to": "bsky.social",
        "fields": ["/text", "/og.title", "/og.description", "/og.image_url"],
        "purpose": "Publish post with link card.",
        "third_party_retention": "persistent-indefinite"
      }
    ]
  },
  "...": "..."
}
```

Before v0.4, this manifest had to either lie about the install layout or
push the blast-radius prose into `scopes[].rationale`. After v0.4, both
the install shape and the variable target are first-class.

## What v0.4 does not include

- **Manifest signing / author identity verification.** Still v0.5+ territory.
- **`runtime.install.layout` Shape B** (structured layout-with-validation
  beyond the v0.3.1 informational hint). Still queued for when a real
  consumer needs it.
- **Standardized eval-suite runner** for `verify.suite.ref`. v0.3
  declared the contract; v0.4 doesn't ship the runner — that lands when
  the trading and gmail-triage signals have enough volume to validate
  the runner shape.
- **`actions[].runtime_telemetry` shape.** Reserved opaque since v0.3.
  Will land in v0.5 once adaptive tool-routing has a concrete consumer.
- **Cross-env dependency declarations** ("obtain X only after Y is set").
  Still v0.5 backlog.
- **Tool-to-tool dependencies.** Unblocked by v0.3.1's `tool.namespace`
  + `tool.id` two-field identity, but the dependency shape itself is
  still open.
