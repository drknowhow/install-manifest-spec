# Install Manifest v0.2 — Design Notes

**Status:** v0.2, 2026-05-05.
**Schema:** [`schema/install-manifest-v0.2.json`](../schema/install-manifest-v0.2.json)
**Predecessor:** [`design/v0.1-design-notes.md`](v0.1-design-notes.md) (frozen)

---

## Why v0.2 exists

v0.1 was MCP-server-shaped without saying so. The `runtime.kind` enum lists
`python-module` and `shell-binary` alongside `mcp-stdio`, but the rest of the
schema only really equips an agent to use the MCP path:

- `runtime.entrypoint.command` is one argv. Fine for "start the MCP server,"
  meaningless for "call the `send` action of a Python CLI."
- `tool.description` is Markdown for humans, with a schema warning that "agents
  should not parse this for behavior."
- `smoke.kind = "mcp-tool-call"` exists; no equivalent for "call the
  `whoami` subcommand."

For an MCP server, the agent connects and discovers tools/operations via the
protocol. For a Python script, a shell binary, or an HTTP API, the agent has
no structured way to learn what operations exist, what arguments they take,
or what shape they return — beyond reading prose the spec told it not to
parse.

v0.2's scope is **one section** that closes that gap: a top-level `actions[]`
catalog of operations, with structured invocation, input, output, and
side-effect declarations. Everything else from v0.1 is preserved.

---

## What v0.2 is NOT

- **Not a full RPC schema.** We are not reinventing OpenAPI or JSON-RPC. The
  catalog is descriptive enough for an agent to drive the tool, not a
  generative substrate for client code.
- **Not signing.** Still deferred. Candidate for v0.3.
- **Not a runtime model change.** `runtime.kind` stays as-is.
- **Not a v0.1 superset URL.** v0.1 manifests stay valid against the v0.1
  schema URL. v0.2 is a separate schema at a separate URL. Agents that only
  understand v0.1 must reject v0.2 manifests outright (forward compatibility
  via ignore-unknown is a known footgun for security-relevant fields — same
  rationale as v0.1's `manifest_version` being a `const`).

---

## What changed from v0.1

1. **`manifest_version`** const bumped to `"0.2"`.
2. **New top-level `actions[]`** array: catalog of agent-callable operations.
   Required when `runtime.kind` is in `{python-module, node-module,
   shell-binary, container, mcp-http}`; optional for `mcp-stdio`.
3. **New `smoke.kind = "action-call"`**: smoke can reference an entry in
   `actions[]` rather than duplicating invocation machinery.
4. **`env[].prompt` cap raised** from 280 to 800 chars. v0.1's cap was tight
   for OAuth-style credentials whose obtain procedures are multi-step (this
   was caught when authoring `examples/gmail.json`, where the original
   `GOOGLE_REFRESH_TOKEN` prompt ran 304 chars and had to be trimmed). Agents
   that need a one-line summary should synthesize one from the prompt's
   first sentence rather than rely on the field being short.
5. **`actions[].invocation`** templating introduces a small, deliberate
   surface: `${input.<path>}` substitutes from validated input,
   `${env.<NAME>}` substitutes from collected env vars. Smoke's existing
   `${VAR_NAME}` syntax (`http` smoke headers/body) is preserved unchanged
   for back-compat.

No existing field is removed or has its semantics altered. v0.2 is
**additive**.

## The new section: `actions[]`

The catalog is an array of operation descriptors. Each entry is the answer
to: *if an agent has this manifest in front of it, can it call this
operation without reading prose?*

### Required vs optional — the lean is **strict**

The schema enforces presence via a top-level `allOf`:

```json
"if": { "properties": { "runtime": { "properties": {
  "kind": { "enum": ["python-module", "node-module",
                     "shell-binary", "container", "mcp-http"] } } } } },
"then": { "required": ["actions"], "properties": { "actions": { "minItems": 1 } } }
```

Rationale: a Python-script tool with no `actions[]` is unusable by an agent
that cannot read minds. The validator should refuse it at publish time, not
at smoke time. `mcp-stdio` is exempt because the MCP protocol provides
discovery; an `mcp-stdio` author who *also* publishes `actions[]` simply
gets the additional metadata (per-action `side_effects`, `idempotent`,
`scopes_used`) that the protocol does not carry.

The alternative — leaving `actions[]` always optional and "strongly
recommended in prose" — was rejected because it leaves us with the same
class of bug the v0.1 spec narrowly avoided by making `manifest_version` a
`const`: silent under-specification.

### Field-by-field rationale

#### `actions[].name` (required)

Pattern `^[a-z][a-z0-9_]{0,62}$` — lowercase snake_case, max 63 chars,
must start with a letter. Snake_case rather than the hyphenated form used
for `tool.id` because action names commonly become Python module attributes
or shell positional arguments where hyphens are awkward (`set -- $action`,
`getattr(mod, name)`).

#### `actions[].invocation` (required)

Discriminated union of four kinds. Each kind requires the fields it
actually needs and forbids the others — same `oneOf` discipline as v0.1's
`runtime.install.method`, for the same reason: catch ill-formed manifests at
publish time rather than at smoke time.

- **`subcommand`** — argv appended to `runtime.entrypoint.command`. Use
  for actions whose input is small and well-quoted: search queries, IDs,
  flags. `argv_template` may contain `${input.foo}` and `${env.FOO}`
  tokens.
- **`stdin-json`** — validated input is sent as a single JSON object on
  stdin. Optional `argv_template` prefix selects the operation. Use for
  actions whose input may be large (email bodies, file contents) or
  contain shell-quoting hazards (newlines, quotes, control chars). On
  Windows, argv has an ~8 KB limit; stdin-json sidesteps the entire
  category.
- **`http`** — for HTTP-kind tools. `path` is appended to
  `runtime.endpoint_url`; may contain `${input.foo}` for path parameters.
  Body (when method allows) is JSON of validated input minus
  path-substituted fields. Headers may reference `${env.FOO}` (auth
  headers). HTTP tools have no argv; forcing a shell-binary fiction here
  would be worse than a proper kind discriminator.
- **`mcp-tool`** — for `mcp-*` runtimes that opt to enumerate operations
  explicitly rather than rely on protocol discovery. `tool_name` must
  match a tool the server exposes.

The templating surface is deliberately small. We do **not** support
arbitrary expressions, transformations, or computed substitutions.
Anything more complex lives in the tool itself, not in the manifest.

**Secrets discipline.** Secrets MUST NOT be templated into argv —
process listings on Linux/macOS make argv readable to other users on
the same host. Manifests that need to pass a secret to an action MUST
use `stdin-json` (body), `http` body, or `http` headers. v0.2 documents
this rule in the field's description; v0.3 may add a validator that
flags `${env.NAME}` substitution into `argv_template` when `env[NAME]`
has `secret: true`.

#### `actions[].input` (optional)

JSON Schema Draft 2020-12. The agent validates input against this before
invocation. Validation must reject unknown properties unless the schema
explicitly permits them. Omit for actions that take no input.

The output of validation is what gets templated into argv / serialized to
stdin / passed as the request body. There is no second normalization pass.

#### `actions[].output` (optional)

Five formats: `json`, `text`, `binary`, `ndjson-stream`, `none`.

- **`json`** — single JSON object/array on stdout (or HTTP response body).
  Recommended `schema` so agents can validate the response.
- **`text`** — opaque text. Agents treat the output as a string.
- **`binary`** — raw bytes. Supported for honesty; tool authors are
  encouraged to return JSON containing a path or URL to a binary artifact
  rather than emitting raw bytes, because most agent transports lose
  binary data.
- **`ndjson-stream`** — one JSON object per line on stdout. The optional
  `schema` describes the per-record shape, not the stream as a whole.
  Agents stream rather than buffer.
- **`none`** — fire-and-forget. Used for write actions whose only signal
  is exit code / HTTP status.

#### `actions[].side_effects` (required)

Four-level severity:

- **`none`** — pure compute. Invoke freely.
- **`read`** — no state change but accesses user data. Mailbox reads
  are `read`, not `none`, because reading private content is
  privacy-side-effecting even when no state mutates.
- **`write`** — creates or modifies state recoverably. Agent decides
  confirmation policy by context.
- **`destructive`** — sends, deletes, or otherwise cannot-undo. Agents
  SHOULD require human confirmation by default, unless an agent-level
  policy explicitly grants autonomous destructive operations.

Why required? Because a missing `side_effects` would force the agent
either to assume the worst (refusing to invoke anything without
confirmation) or to assume the best (invoking destructive operations
silently). Both fail-open and fail-closed defaults are wrong in
different ways; the manifest must declare.

#### `actions[].idempotent` (optional, default `false`)

Default-false because the safer assumption when in doubt is "don't
retry." Tools opt in. An idempotent action is one where repeated calls
with the same input have the same effect as a single call — this lets
agents safely retry on transient failure (timeouts, transient HTTP 5xx).

#### `actions[].scopes_used` (optional)

Array of strings. Each entry should resolve to a top-level
`scopes[].resource`. Lets agents reason about least-privilege per call:
if the user has approved `gmail.messages: [read]` only, an action
listing `gmail.messages` in `scopes_used` whose argument requires
`send` should be flagged before invocation.

v0.2 leaves the cross-reference check as a validator warning rather than
a schema-level error, so manifest authors can iterate without churning
the schema file.

#### `actions[].error_envelope` (optional, default `"raw"`)

Two values:

- **`standard`** — on failure, the action returns
  `{"error": {"code": string, "message": string, "details"?: object}}`.
  Agents can rely on this shape for error-handling logic.
- **`raw`** — the tool's native error shape is opaque to the agent.

Default `raw` so v0.2 imposes no refactor on existing tools that already
have an error shape. New tools should prefer `standard`. v0.3 may flip
the default once enough manifests have migrated.

#### `actions[].examples` (optional)

Up to four `(description, input, output)` triples. Documentation, not
contract; agents should not learn behavior from examples that the
structured fields fail to capture. Useful for IDE-style hover, for
documentation generators, and for the registry's tool-detail page.

### `smoke.kind = "action-call"`

New smoke kind that references an entry in `actions[]` by name:

```json
"smoke": {
  "kind": "action-call",
  "action": "whoami",
  "arguments": {},
  "success": { "no_error_field": true,
                "json_pointer_equals": { "/email": "${GOOGLE_USER_EMAIL}" } }
}
```

Rationale: the smoke test should exercise the same invocation
machinery the agent uses at runtime, not a parallel one. If `whoami` is
broken, the smoke test fails the same way the agent's first call would
fail. Validators should additionally check that
`smoke.action` resolves to an entry in `actions[]` whose `side_effects`
is `none` or `read`.

## Worked example

`examples/gmail.v0.2.json` — full v0.2 manifest for a hypothetical
`yep-gmail` Python module. Five actions: `whoami`, `search`, `send`,
`label_thread`, `unlabel_thread`. Exercises all four invocation kinds
(`subcommand` for whoami/search; `stdin-json` for send/label/unlabel),
the full `side_effects` spectrum (read for whoami/search, write for
labels, destructive for send), `idempotent` on the read/write actions
but not send, `scopes_used` cross-referencing the top-level
`scopes[]`, and the new `smoke.kind = "action-call"` reusing
`whoami` as the smoke witness.

If the schema cannot describe this without ambiguity, it is not ready.
The example is intentionally not a real package on PyPI — it is the
shape we want, not the artifact we have. Path 2 of the toolspace
roadmap (extracting Yep's Gmail capability into a standalone package)
is what makes this manifest correspond to a real install.

## Migration

- **v0.1 manifests stay valid against v0.1 schema.** The v0.1 schema URL is
  frozen.
- **v0.2 manifests must declare `manifest_version: "0.2"`.** Agents that
  only support v0.1 must reject v0.2 manifests outright.
- **v0.1 examples in the spec repo stay.** `examples/gmail.json` (v0.1)
  remains; the new `examples/gmail.v0.2.json` is its v0.2 sibling, not a
  replacement.
- **CLI.** `install-manifest validate` learns to dispatch on
  `manifest_version` and pick the right bundled schema. Both
  `_data/install-manifest-v0.1.json` and `_data/install-manifest-v0.2.json`
  ship inside the package, both byte-identity-tested against the canonical
  `schema/` files.

## Open design questions (v0.2 → v0.3 backlog)

1. **Secrets-in-argv linter.** v0.2 documents that `${env.NAME}` MUST
   NOT be templated into `argv_template` when `env[NAME].secret` is true.
   v0.3 should add a validator that enforces it.

2. **Cross-action ordering.** `actions[]` is a flat list. Some actions
   logically depend on others (`get_message_id` before `delete_message`).
   v0.2 leaves ordering implicit; v0.3 may add `actions[].depends_on`.
   Current lean: do nothing until a real author hits the gap.

3. **`scopes_used` cross-reference enforcement.** v0.2 leaves it a
   validator warning. v0.3 may promote to a schema-level constraint
   once a vocabulary file (see v0.1 open Q #2) firms up.

4. **Rate / cost per action.** `cost` is tool-level. Some actions are
   far more expensive than others (a deep search vs a whoami). v0.3 may
   add `actions[].cost_cents_estimate` for budgeting. Risk: invites
   tool authors to lie. Lean: defer until estimate_url shows real use.

5. **Streaming progress events.** `ndjson-stream` outputs are line-delimited
   JSON. We do not currently distinguish progress events from final
   results within the stream. v0.3 may add a discriminator
   (`{"event": "progress" | "result" | "error"}`). Lean: see what real
   ndjson-stream tools do first.

6. **`mcp-tool` invocation kind for `actions[]`.** This was added so
   `mcp-stdio` authors can publish a structured catalog alongside the
   protocol's own discovery. It is currently identical in shape to the
   existing `smoke.kind = "mcp-tool-call"`. v0.3 may unify the two if
   nothing has diverged.

7. **YAML support.** Same question as v0.1's open Q #1; same lean:
   JSON-only until real authors complain.

PRs welcome on any of these.

---

## Drift caution

This is an **additive** change to the spec. v0.2 adds capability without
narrowing what v0.1 manifests can express. No existing field semantics
change. No registry-side breaking changes — `manifests.json` keeps the
same shape; agents that only know v0.1 just skip v0.2 entries. The schema
URL is new; the v0.1 URL stays at its frozen contents.

The one place v0.2 narrows v0.1 is in the `if/then` requiring `actions[]`
for non-mcp-stdio runtimes. This is intentional: a non-MCP tool with no
actions catalog is not just under-documented, it is unusable by the
intended consumer. Forcing the catalog at the schema level makes the
failure mode loud at publish time rather than silent at install time.
