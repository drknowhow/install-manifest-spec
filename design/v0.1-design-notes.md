# Install Manifest v0.1 — Design Notes

**Status:** v0.1, 2026-05-05.
**Schema:** [`schema/install-manifest-v0.1.json`](../schema/install-manifest-v0.1.json)

---

## What this spec is

A JSON document an autonomous agent can fetch, parse, and act on to install + verify a third-party tool. The contract is between three parties:

1. **The seller** — the tool author. They publish a manifest at a URL.
2. **The agent** — a buyer. It reads the manifest, prompts its owner for credentials, runs the smoke test, and persists the install.
3. **The human owner** — the person whose money and credentials are being committed. They see the scopes and the cost; they grant or deny.

A registry hosting manifests is **not** a party to the contract. A registry indexes manifest URLs and may run sanity-check pipelines, but a manifest is consumable directly without going through any registry. That's deliberate: the spec is the moat, not any single registry. Other registries can host the same manifests; agents can install from raw GitHub URLs.

---

## What this spec is NOT (v0.1)

Out of scope, by design:

- **Identity / signature.** No notion of "this manifest is signed by author X." Agents take the manifest at face value. Trust comes from registry pre-publish checks and from agent-emitted reviews. v0.2 will add signing.
- **Versioning of the contract beyond `manifest_version`.** A v0.2 schema will be a separate file at a new URL. We do not try to forward-evolve a single document.
- **Cross-tool dependencies.** A manifest describes one tool. If it requires another tool to be installed first, that's the agent's problem to resolve.
- **Cross-env dependencies.** `env[]` is a flat list. If `GOOGLE_REFRESH_TOKEN` is only obtainable after `GOOGLE_CLIENT_ID` is set, that ordering lives in the prompt text, not the schema. Likely candidate for v0.2.
- **Live state.** A manifest is static. Run-time status (is the tool currently up? what's my balance?) lives in separate APIs.

## Field-by-field rationale

### `manifest_version` (required, const "0.1")

Pinned. Not SemVer-y. v0.1 is the only valid value for this schema. When v0.2 ships, it gets its own schema URL and its own constant.

Why constant rather than range: agents that support v0.1 should reject v0.2 manifests outright rather than silently dropping unknown fields. Forward compatibility through ignore-unknown is a known footgun for security-relevant fields like `scopes`.

### `tool` (required)

Identity. The five required fields (`id`, `version`, `name`, `summary`, `homepage`) are the minimum to populate a search result and a confirmation dialog.

- `id` is the primary key in any registry. Lowercase + hyphenated; pattern guarantees URL-safe.
- `version` is SemVer of the tool itself, distinct from `manifest_version`.
- `summary` is capped at 280 chars (agents will display it inline).
- `description` is optional Markdown for humans. Agents are explicitly told not to parse it for behavior.

### `runtime` (required)

How the tool is acquired and how the agent invokes it. The `kind` enum bounds the support surface — six options is enough to cover MCP servers, network endpoints, and traditional CLI tools without becoming a generic execution spec.

`install.method` is a discriminated union. Each method requires the fields it actually needs and forbids the others. This catches a class of bug where a manifest declares `method: "git"` but only includes `package` — under a permissive schema that would silently fail at install time.

The `url`-method case requires `sha256` because direct downloads are the highest-risk install path. Other methods either pin via package-manager semantics (`pip` with `==`, `npm` with exact) or require `ref` for git.

### `env` (optional, but usually present)

Each entry describes one prompt the agent will deliver to its owner. Three properties matter:

- `secret` is the single most important boolean in the manifest. It tells the agent whether the value can appear in logs, completion contexts, and error messages, or must be quarantined to the host's secret backend.
- `validation_regex` is for retry-loop UX. If the user mistypes a token, the agent can detect and reprompt rather than failing the smoke test 30 seconds later.
- `obtain_url` lets the manifest deep-link to the credential creation page. This is the difference between "install in 60 seconds" and "install in 20 minutes."

`name` is required to be SCREAMING_SNAKE_CASE for two reasons: it matches the convention the values will be used under (env vars), and the regex pattern `^[A-Z][A-Z0-9_]*$` rules out a class of injection-shaped names.

### `scopes` (optional)

Permission declarations. Each scope is a (resource, actions, rationale) triple. The agent surfaces this list to the human owner as the consent screen. The `provider_scope` field is optional metadata that lets a credential-aware agent verify the tool's declared scope matches the OAuth scope it actually requested — useful for catching scope-creep attacks.

The `actions` enum is intentionally short (`read`, `write`, `delete`, `send`, `execute`, `admin`). Six verbs that map cleanly to common API patterns. We resisted vendor-specific verbs (`forward`, `archive`) because they don't generalize and the rationale field is where nuance lives.

### `smoke` (required)

This is the linchpin of the whole spec. Without a smoke test, "install succeeded" reduces to "install command returned exit 0," which is meaningless for credential-gated tools.

Three smoke kinds cover the realistic cases:

- `shell` — run a CLI command, check exit + stdout.
- `http` — for hosted tools, hit a verification endpoint with the user's credentials.
- `mcp-tool-call` — for MCP servers, invoke a known-safe tool exposed by the server itself (e.g., a `health` or `whoami` tool).

`success` is structured (`exit_code`, `http_status`, `stdout_regex`, `body_regex`, `json_pointer_equals`, `no_error_field`) rather than free-form because agents need to know precisely what counts as success.

Logical AND across present fields. We considered OR but it complicates manifest authoring without obvious benefit; sellers who want OR can add a wrapper script.

### `kill_switch` (required)

Required. Non-negotiable. An agent that cannot revoke a tool is an agent that cannot recover from a compromised credential. Three kinds, in order of preference:

- `url` — DELETE an endpoint. Cleanest; agent does it autonomously.
- `shell` — run a revocation command. Acceptable for local tools.
- `manual` — surface instructions to the human. Last resort.

Registry pre-publish smoke pipelines should exercise the kill switch to confirm it actually works. A manifest where the kill switch URL 404s should be rejected.

### `cost` (optional)

Cents-denominated to dodge floating-point precision arguments and to match how Stripe stores money. `usage_model: "external"` is the escape hatch for tools that bill via their own credentials — the registry/marketplace is not in the payment loop, but the field still tells the agent "this is not free."

`estimate_url` lets a sophisticated tool publish a real-time estimator. Agents that don't support live estimation can ignore it.

### `support` (optional)

Three URLs/email for filing bugs, security issues, and reading docs. Optional but strongly encouraged.

## Open design questions (v0.1 → v0.2 backlog)

1. **YAML support.** Schema is JSON. Should the spec also accept YAML for human-edited manifests? Adds a parsing layer but improves authoring UX. Current lean: JSON-only for v0.1, add YAML in v0.2 if real authors complain.

2. **Scope vocabulary.** `scopes[].resource` is a free string with examples. Should we define a controlled vocabulary in a separate file (`scopes-vocabulary-v0.1.json`)? Pros: agents can policy-check against a known list. Cons: every new resource type needs a spec bump. Current lean: free string in v0.1, draft a vocabulary file alongside but mark it advisory.

3. **Smoke test sandbox.** When a registry runs the seller's smoke test pre-publish, do we run it in a fresh container with throwaway credentials, or trust seller-provided tests will be benign? Current lean: throwaway containers. Security posture is much cleaner.

4. **`runtime.install.method` extensibility.** Five methods (pip, npm, git, container, url) cover ~95% of the MCP ecosystem today. Missing: cargo, gem, go install, brew. Current lean: ship v0.1 with the five and accept that some sellers will need to wrap (e.g., a Rust tool publishes a binary URL with sha256 rather than `cargo install`). Add language-native methods in v0.2 based on real demand.

5. **Manifest URL discovery.** A tool's manifest lives at... where? Three options: (a) registry-only; (b) any URL the seller declares; (c) a `.well-known` path on the tool's homepage (`example.com/.well-known/install-manifest.json`). Current lean: (b) and (c) both work; registries index either.

6. **`env[].prompt` length cap.** v0.1 caps `env[].prompt` at 280 chars, copied from the `summary` field's "displayed inline" rationale. In practice this is too tight for OAuth-style credentials whose prompt needs to include a multi-step obtain procedure (caught when the gmail example was written — the original `GOOGLE_REFRESH_TOKEN` prompt ran 304 chars and had to be trimmed). Current lean: bump the cap to 800 or 1000 in v0.2; agents that need a one-line summary can synthesize one from the prompt's first sentence rather than rely on the field being short.

PRs welcome on any of these.
