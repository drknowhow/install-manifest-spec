# Install Manifest v0.3 — Design Notes

**Status:** v0.3 design, frozen 2026-05-06.
**Predecessor:** `design/v0.2-design-notes.md` (frozen).
**Schema:** `schema/install-manifest-v0.3.json`.
**Worked example:** `examples/gmail.v0.3.json`.

---

## Why v0.3 exists

v0.1 made tools installable. v0.2 made them *callable* via a structured
`actions[]` catalog. Neither version answers two questions an agent
installing from a marketplace must answer:

1. **Does this tool actually work right now, and how would I know if it
   stopped working?** v0.2 has `smoke` — a one-shot install-time check.
   It is silent on degradation after install, on a richer eval suite,
   and on what "working" means at the SLA level. A marketplace whose
   manifests can't carry a verification contract reduces to npm with
   marketing copy.
2. **What does this tool do with the user's data?** v0.2's `scopes[]`
   declares the verbs the tool will exercise on resources (`read`,
   `write`, `send`...). It says nothing about whether private content
   transits a third-party endpoint, whether anything is persisted, or
   for how long. An agent acting on behalf of a user whose data is
   subject to GDPR / sectoral privacy rules cannot make defensible
   install decisions without a data-boundary declaration.

A third, smaller concern surfaced by EASYTOOL (Yuan et al., 2024) and
banked from the LLM-agent survey (Chowa et al., arXiv:2508.17281v2):
**verbose tool documentation degrades agent performance**. v0.2 caps
`actions[].description` at 4000 chars with no internal structure.
That's plenty of room to under-perform.

v0.3's scope is three additive sections that close those gaps:

- top-level `verify` — augments `smoke` with optional suite + SLA
- top-level `data_boundary` — reads / transmits / persists / retention
- `actions[].docs` — concise structured prose, capped per field

Plus one **reserved-but-no-op** field, `runtime_telemetry`, so v0.5
can add adaptive-routing telemetry without re-migrating v0.3
manifests.

Everything from v0.2 is preserved.

---

## What v0.3 is NOT

- **Not a runtime-telemetry implementation.** The field name is
  reserved; the validator accepts it as an opaque object; no agent
  behavior keys off it in v0.3. v0.5 fills it in. Reserving now
  prevents the v0.5 schema bump from invalidating in-flight v0.3
  manifests.
- **Not a substitute for `smoke`.** `smoke` stays required and stays
  one-shot. `verify` adds *more* verification, not different.
- **Not signing.** Still deferred. Now a candidate for v0.4.
- **Not a privacy audit.** `data_boundary` is a self-declaration by
  the tool author; agents and humans must still apply their own
  judgment. The marketplace SHOULD lint declarations against
  observed behavior over time, but the lint is not part of the
  manifest contract.
- **Not a v0.2 superset URL.** v0.2 manifests stay valid against the
  v0.2 schema URL. v0.3 is a separate schema at a separate URL.
  Same forward-compat discipline as v0.2.

---

## What changed from v0.2

1. **`manifest_version`** const bumped to `"0.3"`.
2. **New top-level `verify`** (optional). Adds `suite` and `sla`
   beyond what `smoke` provides. Designed so manifests with only a
   smoke can omit `verify` entirely — they pay nothing for the new
   capability if they don't use it.
3. **New top-level `data_boundary`** (conditionally required — see
   below). Declares which resources the tool reads, what data it
   transmits to third parties, what it persists, and retention.
4. **New `actions[].docs`** (optional). Structured prose with
   per-field caps (goal/inputs/outputs/errors/example, each ≤ 200
   chars). Coexists with `actions[].description` (unchanged).
5. **Reserved `actions[].runtime_telemetry`** (optional, opaque
   object, no v0.3 semantics). Forward-compat for v0.5.
6. **No removed fields. No changed semantics on existing fields.**
   v0.3 is **additive**, with one narrowing carve-out (see
   `data_boundary` below).

## The new section: `verify`

`smoke` answers: *did install succeed?* `verify` answers: *is the
tool still working, and how would the agent know if it weren't?*

### Shape

```json
"verify": {
  "suite": {
    "ref": "./eval/suite.jsonl",
    "format": "jsonl-cases",
    "pass_threshold": 0.9,
    "case_count": 12
  },
  "sla": {
    "p50_latency_ms": 500,
    "p95_latency_ms": 2000,
    "error_rate_max": 0.05
  },
  "schedule": {
    "cadence": "daily",
    "on_install": true
  }
}
```

All four sub-blocks are optional. A manifest that wants only an SLA
declaration sets `verify.sla` and omits the rest. Authors who want
the full surface ship a suite, an SLA, and a cadence.

### Field-by-field rationale

#### `verify.suite` (optional)

- `ref` — relative path inside the manifest's distribution to a
  test-case file. Path is resolved relative to the manifest URL.
- `format` — `"jsonl-cases"` (one `{input, expected}` record per line)
  is the only supported format in v0.3. Future formats are an
  enum-extension migration; we keep the door open by making this an
  enum, not a const.
- `pass_threshold` — a real number in `[0, 1]`. The fraction of cases
  that must pass for the suite to pass overall. Default `1.0` (all
  must pass). Below 1.0 acknowledges that some agent-driven cases
  have nondeterministic surface (LLM grading, timing, third-party API
  flakiness) and the author has chosen a tolerance.
- `case_count` — declared count of cases. Lets the validator catch
  drift between the JSONL file and the manifest's claim.

We deliberately DON'T standardize the per-case grading semantics.
Cases are interpreted by a runner the manifest distribution provides;
the manifest tells the runner where the cases live, not how to grade
them. This mirrors v0.2's choice to keep `actions[].description`
prose-only — the structured contract is the invocation, not the
content.

#### `verify.sla` (optional)

Three numeric hints for monitoring. `p50_latency_ms`, `p95_latency_ms`,
`error_rate_max`. All optional. None of these are enforced by the
manifest; they are *contract claims* a marketplace can use to:

- Display "expected response time" on the package page.
- Flag a tool whose runtime metrics drift outside the declared
  envelope.
- Let an agent route around tools currently breaching their own SLA.

Default discipline: omit `sla` entirely rather than guess. False
specificity here is worse than no claim.

#### `verify.schedule` (optional)

When the marketplace (or the installing agent) re-runs `verify`.
- `cadence` — `"on-install" | "daily" | "weekly" | "manual"`. Default
  `"on-install"`.
- `on_install` — boolean. Whether to run the suite as part of the
  initial install handshake (after `smoke` passes). Default `false`
  — install handshake stays cheap; suite is opt-in.

### Why `verify` is a sibling of `smoke`, not a parent

Two reasons:

(a) **Migration.** Nesting `smoke` under `verify.smoke` would force
every v0.2 manifest to migrate. Keeping `smoke` at top level lets a
v0.2 → v0.3 bump be just `manifest_version: "0.3"` plus optional
adds.

(b) **Semantics.** `smoke` is a *gate*: install fails if it fails.
`verify` is a *contract*: ongoing claims about what working looks
like. They have different lifecycles; conflating them in nesting
would invite authors to put gate-strength assertions in the
contract block or vice versa.

## The new section: `data_boundary`

### Shape

```json
"data_boundary": {
  "reads": [
    { "resource": "gmail.messages", "sensitivity": "high" }
  ],
  "transmits": [
    {
      "to": "api.openai.com",
      "fields": ["gmail.messages.body"],
      "purpose": "classification",
      "third_party_retention": "none-per-vendor-tos",
      "vendor_tos_url": "https://openai.com/policies/api-data-usage-policies"
    }
  ],
  "persists": [
    { "where": "tool_local", "fields": ["last_processed_msg_id"] }
  ],
  "retention": {
    "tool_local_days": 30,
    "transmit_log_days": 7
  }
}
```

### Required when?

`data_boundary` is **required** when ANY entry in `scopes[]` declares
`read`, `write`, `delete`, or `send` on a resource matching the
inline pattern
`^(gmail|calendar|drive|contacts|messages|sms|files|photos|location|health|finance|payments|stripe|plaid)\.`.
(Vendor-neutral prefix list — meaning "private user data domains.")

Enforced via top-level `allOf`/`if`/`then`, same idiom as v0.2's
`actions[]` requirement.

The pattern is deliberately narrow — pure-compute tools (no scopes,
or scopes only on `net.outbound` or `fs.tmp`) don't need to declare a
data boundary they don't touch. The pattern can be extended in
v0.4 without churning v0.3 manifests; tools whose scopes don't match
the pattern can opt in voluntarily.

**Decision (locked at v0.3 freeze):** the regex is held inline in the
schema for v0.3. v0.4 may externalize to a vocabulary file once we
have ≥3 manifests in the wild and have observed which prefixes
actually need pruning or extension. Inline is one place to edit; an
external vocabulary needs its own versioning story before the cost is
worth paying.

### Field-by-field rationale

#### `reads[]`

What private data the tool sees, even if no state changes. Cross-
references `scopes[].resource`. The `sensitivity` field
(`"low" | "medium" | "high"`) is the author's claim about how
sensitive the read content is — a Gmail subject line is medium, a
full message body or financial transaction list is high.

#### `transmits[]`

The point of the section. Each entry declares one third-party
recipient.

- `to` — domain. Bare hostname, no scheme. The tool MAY contact
  subdomains; declaring `api.openai.com` covers `*.api.openai.com`
  but NOT `*.openai.com`. Authors who use the same vendor through
  multiple subdomains list each.
- `fields` — JSON-pointer-ish expressions over the `reads[]`
  resources, naming what is transmitted. `["gmail.messages.body"]`
  is more specific than `["gmail.messages"]` — declare the
  narrowest accurate field.
- `purpose` — short prose. What this transmission is for.
  `"classification" | "translation" | "storage" | "model-inference"
  | "logging"` are the suggested vocabulary; free-form is allowed.
- `third_party_retention` — controlled enum:
  `"none-per-vendor-tos" | "session-only" | "persistent-30d"
  | "persistent-90d" | "persistent-indefinite" | "unknown"`.
  `"unknown"` is an explicit option because authors who genuinely
  don't know SHOULD declare that rather than fabricate a claim.
- `vendor_tos_url` — required when `third_party_retention` is
  `"none-per-vendor-tos"`. Lets a downstream agent verify the claim
  against the vendor's actual stated policy.

#### `persists[]`

What the tool itself stores after the call returns. Per entry:
- `where` — `"tool_local" | "tool_cloud" | "session_only"`.
  `tool_cloud` is "the tool author's own cloud," distinct from
  third-party `transmits[]`.
- `fields` — what's stored.

#### `retention`

Numeric retention windows (in days) for the tool's own storage.
Declared per `where` value; `tool_local_days` and
`transmit_log_days` are the two common ones.

### What we deliberately do NOT include

- **PII categories.** The temptation is to add a categorical taxonomy
  (PII / PHI / financial / behavioral). Rejected: agents and
  marketplaces benefit more from concrete field paths
  (`gmail.messages.body`) than from author-asserted categories that
  invite under-declaration.
- **Encryption claims.** "Encrypted at rest" is largely meaningless
  without specifics, and authors cannot reliably attest to
  third-party encryption practices. v0.4 may add
  `transit_security` (`"tls13" | "tls12" | "plaintext"`) once that
  surface is worth modeling.
- **Data-residency claims.** Cross-jurisdictional data residency is
  a regulatory minefield we don't have authority to resolve in a
  manifest. Tools that need to express it should do so out-of-band.

## The new section: `actions[].docs`

EASYTOOL's finding: agents perform measurably better when tool
docs are concise and structured than when they are long-form prose.
v0.2 already keeps invocation/input/output/side_effects as the
structured behavioral contract; `actions[].description` is the
catch-all 4000-char prose escape hatch.

v0.3 introduces an optional, narrowly capped, structured docs
sub-object that an agent can consume cheaply.

### Shape

```json
"actions": [
  {
    "name": "send",
    "docs": {
      "goal": "Send an email message via the user's Gmail account.",
      "inputs_brief": "to (RFC5322), subject (≤120 chars), body (Markdown), thread_id (optional)",
      "outputs_brief": "{message_id, thread_id, sent_at}",
      "errors_brief": "auth_expired, rate_limited, invalid_recipient",
      "example": "send to=alice@x.com subject='Hi' body='Test.'"
    }
  }
]
```

### Field-by-field rationale

All five fields capped at **200 chars**. The cap is the design.
Authors who can't compress to 200 chars per field may keep using
`actions[].description`; they don't get the structured docs benefit.

- `goal` — what the action accomplishes, agent-readable.
- `inputs_brief` — comma-separated parameter notes. NOT a substitute
  for the `input` JSON Schema, which is canonical. Just a
  human-readable summary.
- `outputs_brief` — same, for output.
- `errors_brief` — comma-separated error codes the action emits.
  Pairs with `error_envelope: "standard"` — when the envelope is
  standard, these codes show up in `error.code`.
- `example` — one canonical invocation. Pairs with
  `actions[].examples[]` (which can hold up to 4 longer-form
  triples); this is the one-liner.

### Why a separate field, not a length cap on `description`?

Because some authors legitimately need 4000 chars of prose for
human readers (caveats, edge cases, deprecation notes). Capping
`description` would force authors to truncate human-facing text.
Adding `docs` lets the same manifest serve both audiences:
`description` for humans browsing the package page, `docs` for
agents at runtime.

Validators MAY warn when both fields say the same thing twice over,
but the schema doesn't enforce one-or-the-other.

## Reserved field: `actions[].runtime_telemetry`

### Shape (v0.3)

```json
"runtime_telemetry": {}
```

Opaque object. No v0.3 semantics. The schema accepts any object.
Validators do not lint its contents. Agents ignore it.

### Why reserve now?

The forcing function is v0.5's adaptive-routing memory. The paper's
AVATAR pattern (per-tool performance ledger feeding contrastive
selection) is real direction; we don't ship it in v0.3 because (a)
no Toolspace tool has competition in its category yet, so adaptive
routing has nothing to route between, and (b) the design space
between agent-side telemetry and marketplace-aggregated telemetry
is unsettled.

But: defining the field name now means v0.3 manifests don't have to
migrate to v0.5. Author writes `runtime_telemetry: {}` once; v0.5
fills in the shape; everything keeps validating.

This is the same forward-compat trick OpenAPI used for `x-` fields
and Kubernetes used for unknown-but-preserved annotations.

## Worked example

`examples/gmail.v0.3.json` — the v0.2 Gmail manifest extended with:

- `verify.suite` pointing at a 12-case JSONL (label routing,
  search, send-with-attachment, thread-fetch, retry-on-429).
  `pass_threshold: 0.92`. `verify.schedule.cadence: "daily"`.
- `verify.sla.p95_latency_ms: 1500`, `error_rate_max: 0.02`.
- `data_boundary.reads`: `gmail.messages` (high),
  `gmail.threads` (high), `gmail.labels` (low).
- `data_boundary.transmits`: NONE (the tool talks only to Google's
  Gmail API; data does not transit a third-party model). This is
  itself the kind of claim the boundary section is FOR — "we don't
  send your mail anywhere except where you'd expect" is exactly
  the trust signal that distinguishes a verified manifest from an
  npm install.
- `data_boundary.persists`: `tool_local` (`last_processed_msg_id`).
  OAuth refresh token is held in the host secret backend, not by
  the tool's own storage, so it does NOT appear under `persists[]`.
- `data_boundary.retention.tool_local_days: 90`.
- `actions[].docs` populated for all five actions, each field
  ≤ 200 chars.
- `actions[].runtime_telemetry: {}` on every action.

The example ships in the same PR as the schema (v0.2 precedent).

## Migration

- v0.2 manifests stay valid against v0.2 schema.
- v0.3 manifests must declare `manifest_version: "0.3"`.
- v0.2 → v0.3 path:
  1. Bump `manifest_version`.
  2. **If** any `scopes[].resource` matches the private-data
     pattern, add a `data_boundary` block. (This is the only
     narrowing in v0.3 — manifests that touch private data
     without declaring a boundary will fail v0.3 validation.)
  3. Optionally add `verify`, `actions[].docs`,
     `actions[].runtime_telemetry`.
- CLI `install-manifest validate` learns to dispatch on
  `manifest_version` to the v0.3 bundled schema. Same shape as the
  v0.1 → v0.2 dispatch.

### CLI surface

The CLI has two distinct subcommands once v0.3 lands:

- `install-manifest validate <path>` — schema-shape check. Pure
  static validation against the bundled schema for the manifest's
  declared version. No network, no execution. This is what v0.2
  shipped and what v0.3 extends.
- `install-manifest verify <path>` — runs the manifest's `verify`
  block (suite + sla checks, when present). Distinct from `validate`
  because it executes the tool's actions. Reserved name in v0.3;
  full implementation lands incrementally — v0.3 ships the schema
  surface and the validate-side dispatch only. The `verify`
  subcommand may be a stub returning "not implemented" in v0.3 if
  it ships at all this cycle. Schema-side compatibility is the
  forcing function; runtime is follow-up.

The two commands answer different questions: `validate` is "is
this manifest well-formed?" and `verify` is "does this tool
currently behave as the manifest claims?". Conflating them under one
verb would either force `validate` to do network I/O or force
`verify` to skip the schema check. Separating them keeps each
command honest about its scope.

## Open design questions (v0.3 → v0.4 backlog)

1. **Suite execution surface.** v0.3 declares `verify.suite.ref`
   and `format`. It does NOT define a runner. v0.4 should standardize
   one — likely a small Python or Node CLI that reads the JSONL
   and exercises the manifest's actions, with pluggable graders.
   Until then, suite execution is per-tool-author.

2. **Marketplace telemetry surface.** Whether the marketplace
   collects anonymized runtime metrics across installations to
   surface aggregate `verify.sla` compliance is policy-loaded.
   Defer until at least 10 tools live with `verify.sla` declared.

3. **Data-boundary lint.** v0.3 self-declarations are honest only
   when a marketplace reviews them. v0.4 may add a static lint
   that grep-checks tool source for declared-vs-undeclared
   network destinations. Limited to source-available tools.

4. **`data_boundary.reads.sensitivity` vocabulary.** v0.3 ships
   `low | medium | high` as author intuition. v0.4 may ground
   these against a controlled vocabulary keyed to scopes.

5. **`docs` localization.** Single English-only `docs.*` fields
   in v0.3. v0.4 may add `docs_i18n: { "es": { ... } }` if any
   real authors complain.

6. **Signing.** Carried over from v0.2. Deferred to v0.4.

7. **`runtime_telemetry` shape.** The whole point of reserving the
   field. v0.5 will land it. Sketch direction: per-call records of
   `{action_name, started_at, ended_at, success, error_code?}`
   posted to a manifest-declared telemetry endpoint or held by the
   agent locally. v0.5 design starts with a forcing function (a
   real category with ≥3 tools).

8. **Private-data prefix list externalization.** Inline regex in
   v0.3 schema. v0.4 candidate to externalize to a versioned
   `vocabularies/private-data-prefixes.json` once usage justifies
   the indirection.

## Drift caution

This is an **additive** change in shape, with one explicit narrowing:
manifests whose `scopes[]` touch private user data MUST declare
`data_boundary`. Every other addition (`verify`, `actions[].docs`,
`actions[].runtime_telemetry`) is opt-in.

The narrowing is intentional. The whole reason `data_boundary`
exists is that an undeclared boundary is a worse default than a
required-but-explicit one. Same shape of argument as v0.2's
required-`actions[]` for non-MCP runtimes: forcing the declaration
at the schema level makes the failure mode loud at publish time
rather than silent at install time.

`runtime_telemetry`'s shape is intentionally undefined in v0.3.
That is forward compatibility, not under-specification. Authors who
include it in v0.3 are signaling readiness for v0.5; agents in v0.3
ignore it.
