# Install Manifest v0.3.1 — Design Notes

**Status:** v0.3.1 additive release, frozen 2026-05-16.
**Predecessor:** `design/v0.3-design-notes.md` (frozen).
**Schema:** `schema/install-manifest-v0.3.1.json`.
**Manifests using new fields:** none yet — the four attesting community
manifests (`muninn-bsky-card`, `muninn-verify-patch`, `muninn-flowing`,
`muninn-perch-publish`) validate unmodified at `manifest_version: "0.3"`
and serve as the regression bed for "additive must not break v0.3."

---

## Why v0.3.1 exists

v0.3 shipped the durable-verification and data-boundary contracts. The
first round of community consumer tests — Oskar Austegard's Muninn agent
authoring four manifests in succession — surfaced six small but
consistent gaps where authors hit the schema and had to either lie a
little or host a pointless wrapper to satisfy a required field. None of
the gaps justify a `manifest_version` bump that breaks existing
manifests. All six are additive: a v0.3.1 schema accepts every v0.3
manifest unmodified.

The forcing signal is **count**: each of these came up in at least one
consumer round, and the install-layout hint hit `count = 4` (every
single Muninn manifest). At four, it's a structural gap, not author
preference.

Source threads (Muninn discussions on
[oaustegard/muninns-inbox#1](https://github.com/oaustegard/muninns-inbox/discussions/1)):

- verify-patch findings: discussioncomment-16868892 / reactions 16870670
- flowing findings: discussioncomment-16870528 / reactions 16870890
- perch-publish findings: discussioncomment-16870978 / reactions 16871046

## Six additive changes

### 1. `kill_switch.kind: "none"` — first-class stateless

v0.3 required every manifest to publish a revocation surface
(`url` / `shell` / `manual`). For tools that hold no credentials, write
no persistent state, and read no consumer-supplied paths
(`muninn-flowing` is the exemplar), the "manual revocation" prose is
performative — the right answer to "how do I revoke this" is "uninstall
the package; nothing else to clean up."

**Shape:**

```json
"kill_switch": { "kind": "none" }
```

**Validator constraint** (schema `allOf`, top-level): `kind: "none"` is
only valid when

- `env` is absent or an empty array
- `data_boundary` is absent, OR `data_boundary.persists` is absent or
  empty

Either check failing forces the author back to `manual` / `url` /
`shell`. Keeps `none` honest: it can only be claimed when there is
literally nothing to revoke.

Note on what's **not** in the validator: "no credentialed scopes." The
v0.3 private-data prefix list (`gmail|calendar|drive|...`) already
forces `data_boundary` whenever such scopes are declared, which in turn
forces `data_boundary.persists` to be evaluated. So the env+persists
check is sufficient — there's no second-class encoding of "credentialed
scope" we need to chase here.

### 2. `kill_switch.manual` — inline `instructions`

v0.3's `manual` kind required `instructions_url`. Authors with
short checklist-form prose (e.g. `muninn-verify-patch`'s four-step
rotate-and-uninstall, `muninn-perch-publish`'s two-surface
rotate-then-content-removal) ended up hosting a wrapper file just to
satisfy the schema.

**Shape** (mutually exclusive — one or the other, never both):

```json
"kill_switch": {
  "kind": "manual",
  "instructions": "1. Rotate the PAT at https://x.\n2. ..."
}
```

`instructions` capped at **2000 chars** — enough for a step-by-step
checklist, short enough to discourage essay-form revocation that
belongs at a URL.

### 3. `tool.namespace` — optional sibling field

The four Muninn manifests adopted a `muninn-` prefix as informal
namespace (`muninn-bsky-card`, `muninn-verify-patch`, `muninn-flowing`,
`muninn-perch-publish`). The prefix is convention, not enforcement —
and the convention leaks the consumer's namespace into the global ID
space.

@oaustegard explicitly tested `tool.id: "muninn/flowing"` against the
v0.3 schema while authoring `muninn-flowing` and was rejected (the
regex doesn't allow slashes); on `muninn-perch-publish` he noted he
would have used `namespace: "muninn"` if v0.3.1 had landed. Present
need with a workaround already in production — not a future need.

**Shape:**

```json
"tool": {
  "namespace": "muninn",
  "id": "flowing",
  "version": "0.1.0"
}
```

`canonical_id := namespace ? "${namespace}/${id}" : id`. Existing
single-field manifests continue to validate (namespace optional). v0.4
can promote `namespace` to required for new manifests if collisions
accumulate, and the `requires:` / `scopes_consumed_from:` cross-reference
resolver in v0.4 uses `f"{ns}/{id}"` as registry key without parsing
slashes out of a single field.

**Why two fields, not relaxed regex.** Relaxing `^[a-z0-9-]+$` to allow
slashes buys nothing structurally — collisions just move from
`muninn-flowing` vs `muninn` to `muninn/flowing` vs `muninn/flow/v2`.
Two fields make the namespace explicit and queryable.

`namespace` regex: `^[a-z0-9][a-z0-9-]{0,30}[a-z0-9]$` (2–32 chars,
hyphenated lowercase, same character class as `id` but shorter).

### 4. `runtime.install.layout` — install-shape hint (Shape A)

Four consecutive consumer manifests hit the same install gap.
`bsky_card`, `verify_patch`, `flowing`, and `perch_publish` all live in
`oaustegard/<repo>/<subpath>` git layouts that aren't pip / npm / cargo
packages. Each one declared `method: "git"` with a `subpath:` and
effectively meant "clone this, set PYTHONPATH or equivalent, run the
entrypoint." Same fiction four times — count is the forcing signal.

**Shape** (added to the `git` install variant):

```json
"runtime": {
  "install": {
    "method": "git",
    "url": "...", "ref": "...", "subpath": "...",
    "layout": "skill-bundle"
  }
}
```

Enum (informational hint, default `package` for back-compat):

- **`package`** — pip / npm / cargo / etc — the canonical case.
- **`skill-bundle`** — SKILL.md + `scripts/` + `tests/` (Claude-skills
  layout). `oaustegard/claude-skills/flowing/` is the exemplar.
- **`raw`** — git+subpath without a recognized layout convention.
  Agents fall back to "clone, set PYTHONPATH, run entrypoint."

The four attesting manifests all become `layout: "raw"` (or
`"skill-bundle"` for `flowing` specifically) when they next ship. No
code changes needed for existing manifests — they remain valid v0.3,
and the layout field is purely informational in v0.3.1.

**Deferred to v0.4 (Shape B):** structured layout-with-validation —
what an agent that "understands" a skill-bundle actually does beyond
the raw fallback. Decided after v0.3.1 ships and we observe what
installers do with the hint.

### 5. `smoke.success.json_pointer_in` — set-membership

Equality is fragile for LLM-generated outputs. `muninn-verify-patch`
returns `verdict ∈ {CORRECT, LIKELY_CORRECT, UNCLEAR}`; both `CORRECT`
and `LIKELY_CORRECT` are valid "smoke passed."

**Shape:**

```json
"smoke": {
  "success": {
    "json_pointer_in": { "/verdict": ["CORRECT", "LIKELY_CORRECT"] }
  }
}
```

Map of JSON Pointer → array of acceptable string values, `minItems: 1`.
Passes if the resolved pointer equals any entry in the array.

### 6. `smoke.success.json_pointer_present` — non-null, non-empty

Same shape as `json_pointer_exists` but stricter. Useful when an
LLM-generated field's existence is the success signal but its content
is open-ended (e.g. `/answer` is non-empty prose, can't be enumerated;
`/layers` and `/total_tasks` exist for `flowing.validate` but values
are graph-shape-dependent).

**Shape:**

```json
"smoke": { "success": { "json_pointer_present": "/answer" } }
```

Difference from `json_pointer_exists`: `_present` additionally requires
the resolved value to be non-null and, if a string, non-empty after
trim. `_exists` accepts `""` and `null` — useful when "the field
appeared" is enough.

## Two design notes (additive, non-schema)

### (a) Frameworks SHOULD NOT publish manifests

Surfaced by the `muninn-flowing` round. A framework whose blast radius
is determined entirely by consumer code is the wrong layer to author a
manifest at.

> Frameworks, libraries, and other pure-compute primitives whose blast
> radius is determined by consumer code SHOULD NOT publish install
> manifests. The manifest contract presupposes the publisher knows what
> scopes, side effects, costs, and revocation steps are involved. For a
> framework, those are properties of the consumer's configuration, not
> the framework itself. Publishing a manifest in that case either lies
> (claims fewer side effects than the consumer's instantiation will
> produce) or is uselessly maximal (claims every possible scope).
> Publish manifests at the layer where the publisher controls the
> surface area — the agent or skill that uses the framework — not the
> framework itself.

This is a design constraint, not a schema constraint — `kind: "none"`
exists for genuinely stateless tooling like flowing, but flowing-the-
framework remains a manifest-anti-pattern. The guidance lives here.

### (b) Smoke-as-permission-check

Surfaced by the `muninn-perch-publish` round. For destructive tools
whose smoke cannot safely perform the destructive action, prove the
auth that the destructive action would require.

> Pattern: for destructive tools where the smoke cannot safely perform
> the destructive action itself, declare a read-only API call against
> the same auth path the destructive action uses, and assert auth
> succeeds. The smoke tests "the agent has the auth needed to do the
> destructive thing" without performing it. Different epistemic check
> than a free-side-effect-free real call (e.g. `whoami` for an
> OAuth-scoped action), but the same useful gate. Examples:
> `gmail.whoami` (free, side-effect-free read on the same OAuth scope
> as send/modify); `perch_publish` smoke (GET `/repos/{target}` via the
> same PAT used for git-data writes, asserting `permissions.push:
> true`).

Pairs naturally with `json_pointer_equals` /
`json_pointer_in` (#5) and `json_pointer_present` (#6) — the
permission-check response often carries an enum value or a
present-but-arbitrary capability listing.

## Out of scope (v0.4 territory)

From verify-patch round:
- Tool-to-tool deps via `requires: [{tool_id, version_spec, optional?}]`
  + `scopes_consumed_from: [tool_id]` — prerequisite (`tool_id`
  identity) is satisfied by v0.3.1's `tool.namespace` + `tool.id`.
- Conditional creds: `required_when: { actions_used: [...] }`
  install-time variant.
- Explicit `secondary_side_effects` field.
- Variable-input cost: `cost.per_action.max_estimate_cents` +
  `scales_with`.
- Smoke cost — design discipline + optional
  `smoke.cost_estimate_cents`.
- Runtime kind for in-container library functions.
- `provider_scope` enum-with-extension.

From flowing round:
- All framework-manifest items moot under design-note (a).

From perch-publish round:
- `data_boundary.writes[]` shape parallel to `transmits[]`, with
  `where ∈ {tool_local, tool_cloud, session_only, user_service,
  public_web}`, `audience ∈ {private, shared, public-readable}`,
  `retention: {kind, days?, note?}` — biggest single v0.4 shape;
  deserves its own design issue.
- `kill_switch.steps: [{kind, step, irreversible?, ...}]` with
  `oneOf({single, steps})` for back-compat. Concrete instance from
  `perch-publish` (credential rotation reversible + content removal
  irreversible).
- `actions[].atomicity: "atomic" | "best-effort" | "stepwise"` with
  default `best-effort`.
- `provider_resources: ["repo:org/name:scope", ...]` for
  narrow-usage declarations (subsumes `bsky-card`'s app-password
  coarseness); lints against runtime telemetry once v0.5 lands.

Two existing v0.4 issues — `#4` (variable-target outbound transmits)
and `#5` (preinstalled install method) — remain open and are
prerequisites for the v0.4 cut. v0.3.1 unblocks them by giving v0.4
clean ID resolution (`namespace` + `id`) to build cross-references on
top of.

## Compatibility

- All v0.3 manifests validate against the v0.3.1 schema unmodified.
  Bumping `manifest_version` from `"0.3"` to `"0.3.1"` is a
  no-op for any manifest that doesn't adopt new fields.
- `runtime.install.layout` defaults to `package` when absent.
- `tool.namespace` is optional; `canonical_id` derivation degrades to
  bare `id` when omitted.
- `kill_switch.kind: "none"` is the only fully new variant. All other
  kinds remain unchanged.
- The CLI's `SUPPORTED_MANIFEST_VERSIONS` grows from
  `("0.1", "0.2", "0.3")` to `("0.1", "0.2", "0.3", "0.3.1")`. v0.3.1
  manifests get schema dispatch to the v0.3.1 bundle; v0.3 manifests
  continue to dispatch to v0.3.
